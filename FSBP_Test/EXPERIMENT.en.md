# FSBP Quality Experiment

[中文说明](EXPERIMENT.md)

## 1. Keep the claims separate

The experiment does not collapse “multi-agent works” and “FSBP works” into one
claim.

| Comparison | Supported claim |
|---|---|
| `direct` vs `multi_fsbp` | Quality change of the complete Agentic Translating method against a strong-model direct baseline |
| `multi_raw` vs `multi_fsbp` | Contribution of body-only annotation isolation relative to complete raw inheritance |
| JSON protocol experiment vs FSBP | Engineering reliability of the content protocol |

If `multi_fsbp` wins, the defensible statement is that the complete multi-agent
FSBP system won on this dataset against this direct baseline. Only a simultaneous
win over `multi_raw` supports attributing part of the gain to annotation
isolation.

## 2. Prevent test-set leakage

- Eight `dev` items are for generalizing error types and tuning prompts.
- Sixteen `test` items are content- and hash-locked. Some were later used during
  prompt and workflow iteration, so current results are development/diagnostic
  evidence rather than an untouched-holdout claim.
- Test annotations, `reviewerChecklist`, and known direct-translation issues must
  not enter generation context.
- Before a formal run, freeze the actual prompt versions, models, parameters,
  code commit, dataset hashes, and baseline provenance.
- Any post-run prompt change requires a new experiment version.

The original v6 Agent variant and v4 direction bundle freeze is retired. The
current product uses the versions recorded in the run manifest; old results must
not be relabeled as current-product results. A future unseen gate requires a
newly frozen holdout that no participant has reviewed or used for tuning.

## 3. Conditions

### direct

One strong model reads the source, task requirements, and direction-wide quality
rules and writes one complete translation.

### multi_raw

Three fixed complementary roles produce candidates. Review, filter, orchestrate,
and assemble receive the complete upstream `raw`, including annotation after the
`---` boundary.

### multi_fsbp

This condition shares candidates, models, parameters, and stage prompts with
`multi_raw`. The only protocol change is that every downstream stage receives
`body` only. Raw output and annotation remain archived for audit.

## 4. Fixed roles

To avoid dynamic role-selection randomness, each category uses a fixed trio:

| Category | Roles |
|---|---|
| poetry | semantic-fidelity + voice-register + poetry-form |
| literary | semantic-fidelity + voice-register + literary-prose |
| cultural_argument | semantic-fidelity + voice-register + dissenting |
| nonliterary | semantic-fidelity + terminology + long-context |

Two preflight imagery/culture analyses are generated by different models and
shared by all multi-agent conditions. They are not included in `direct`.

## 5. Blind review

- The three final translations for each item are randomly labeled A, B, and C.
- Model, condition, Agent, annotation, and generation order are hidden.
- The current human reviewer is recorded as `internal-human, n=1`.
- Model reviewers record provider, model version, date, and scoring prompt.
- Reviewers score independently, then use the existing human issue list only for
  a missed-issue check.
- Missing scores are not fabricated, and results are not edited to reach an
  expected win rate.

Scoring dimensions are defined in `rubrics/translation-quality.md`.

## 6. Run artifacts

Real outputs live under the Git-ignored `FSBP_Test/results/<run-id>/` directory:

```text
manifest.json
raw.jsonl
final.jsonl
blind-review.md
blind-key.json
scores/
report.md
```

Configuration files must not contain API keys. Secrets are read from environment
variables only.
